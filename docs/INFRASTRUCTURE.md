## 1. Суть одной строкой

Сервер принимает до 8 независимых RTMP-стримов с телефонов (по одному на татами)
и **непрерывно** держит выход на видеоплатформы: когда телефон пропадает, на
выходе автоматически подставляется зацикленная стоп-карта, при возврате — живое
видео. Оператор управляет всем через веб-панель.

## 3. Из чего состоит стек (4 контейнера)

| Контейнер | Образ | Роль |
|---|---|---|
| `tl-mediamtx` | `bluenviron/mediamtx:latest` | RTMP-приём `:1935`, HLS-превью `:8888`, HTTP API `:9997` (внутр. сеть), 16 объявленных путей |
| `tl-supervisor` | `tl-supervisor:local` | **Главный «мозг» непрерывности**: цикл каждые 2 с — держит ровно один FFmpeg-фидер в `broadcast/<x>` для каждого **активного** экрана (live-копия входа или зацикленная стоп-карта; неактивные экраны спят). Плюс контрольный сервер `:8090` (`/state`, `/outputs`, `/labels`, `/screens`, `/end/<x>`, `/resume/<x>`) |
| `tl-relayer` | `tl-relayer:local` | Ретрансляция `broadcast/<x>` → площадки (YouTube/VK/...). Перечитывает `outputs.local.conf` каждые 3 с, hot-reload ключей без рестарта; один ffmpeg на пару «буква+адрес» (несколько площадок на одно татами — поддерживается) |
| `tl-caddy` | `caddy:2-alpine` | Фронт панели `:80`: BasicAuth, статика кокпита, прокси `/v3` → API mediamtx, `/ctl` → supervisor |

### Что чем управляется (цепочка управления)

```
systemd (tl-streaming.service)
   └── docker compose (deploy/vps/docker-compose.yml)  ← вся оркестрация
        ├── mediamtx    — транспорт: принимает/даёт/пишет, решения не принимает
        ├── supervisor  — ЕДИНСТВЕННЫЙ, кто решает live/fallback/ended (цикл 2 с)
        │     ├── 8 × ffmpeg-фидер (live-копия или -stream_loop стоп-карты)
        │     └── ctl.py :8090 — операторский API (кнопки панели, ключи площадок)
        ├── relayer     — доставка: reconcile-цикл 3 с, ffmpeg на каждую строчку конфига
        └── caddy       — доступ: аутентификация + прокси (сам ничего не решает)
```

Панель (kokpit «TournamentLive Flight Deck») — тонкий клиент: только HTTP-запросы
к `/v3` (статусы путей), `/ctl` (кнопки, ключи) и `/hls` (превью). Логики нет.

### Как Supervisor принимает решения

- Опрос API mediamtx: `GET /v3/paths/get/tatami/<x>` → поле `online` (единственный
  источник правды о входе).
- Входящий онлайн → фидер `ffmpeg -i tatami/<x> -c copy → broadcast/<x>` (без перекодирования).
- Входящий офлайн → фидер `ffmpeg -stream_loop -1 fallback_<x>.mp4 → broadcast/<x>`.
- Кнопка «Завершить» (intent `ended` в `/control/<x>`) → фидер убивается, выход
  offline, **не восстанавливается сам** до «Возобновить». Площадка корректно
  показывает «трансляция завершена».
- Фидер умер сам (ffmpeg упал) → на следующей итерации перезапуск.
- Инвариант: ровно один фидер на букву; переключение = ~1–2 с дыра (MVP-ограничение).

## 4. Как осуществляется передача данных

```
Телефон (TournamentLive, Android)
  │  RTMP push: rtmp://172.22.22.17:1935/tatami/   + ключ = НОМЕР ЭКРАНА (1..8)
  ▼
[mediamtx]  приём RTMP :1935  ──►  16 путей (tatami/1..8, broadcast/a..h = экраны 1..8)
  │                                   ├─ HLS :8888 (превью, on-demand, hlsAlwaysRemux: no)
  │                                   ├─ API :9997 (внутр. docker-сеть, наружу не торчит)
  │                                   └─ record: no (запись ВЫКЛЮЧЕНА на сервере)
  ▼
[supervisor]  читает online-статус tatami/<N> по API (каждые 2 с); ключ N кормит экран N
  │  ffmpeg -c copy (live)  или  ffmpeg -stream_loop -1 fallback_<x>.mp4 (стоп-карта)
  ▼
  RTMP-публикация: rtmp://mediamtx:1935/broadcast/<a..h>   (внутр. docker-сеть)
  ▼
[relayer]  построчно из outputs.local.conf:  <буква> <полный RTMP URL площадки с ключом>
  │  ffmpeg -i rtmp://mediamtx:1935/broadcast/<x> -c copy -f flv <URL площадки>
  ▼
YouTube  (rtmp://a.rtmp.youtube.com/live2/<ключ>)   ·   VK  (полный URL из панели)
                                              ·   несколько площадок на одну букву — можно

Оператор:
  браузер ──HTTP:80──► [caddy] (BasicAuth)
                         ├─ GET  /          → кокпит (статусы входов/выходов, кнопки, ключи)
                         ├─ GET  /v3/*      → API mediamtx (статусы путей)
                         ├─ GET/POST /ctl/* → supervisor (END/RESUME, ключи, /status)
                         └─ превью:  http://172.22.22.17:8888/broadcast/<x>/  (HLS, hls.js)
```

Ключевое разделение: **вход и выход — разные пути**. Площадки и панель никогда
не читают `tatami/*` (то, что делает телефон) — только `broadcast/*` (то, что
держит supervisor). Поэтому обрыв телефона снаружи невидим: меняется источник
выхода, а не сам факт выхода.

### 4.1 Индикатор входа: ИДЕТ / ОБРЫВ / СВОБОДЕН

Из-за того разделения «стрём идёт» и «ключа нет» — РАЗНЫЕ вещи: телефон моргает
(RTMP-соединение рвётся и через 2–3 с поднимается), а картинка на площадке и в
превью остаётся — и потому что supervisor держит `broadcast/*`, и потому что HLS-
плеер и YouTube играют свой буфер в несколько секунд. Окрасить такое моргание
красным «СВОБОДЕН» по одному снимку API — значит получить индикатор, которому
перестают верить. Поэтому состояние входа определяется тем, СКОЛЬКО ключ не
виден, а не тем, виден ли он в этом снимке:

| Вход | Что значит | Порог |
|---|---|---|
| `ИДЕТ · ключ N` (зелёный) | публикация есть сейчас | — |
| `ОБРЫВ · ключ N` (жёлтый) | связь телефона моргнула, картинка ещё из буфера | входа нет < 12 с |
| `СВОБОДЕН · ключ N` (красный) | экрана у оператора нет | входа нет ≥ 12 с |

Длительность берётся из `GET /ctl/status` — supervisor сам пишет на каждый экран
`/control/<буква>.state` (`key=online|offline`, `edge` — когда состояние сменилось,
`feed=live:N|fallback:<файл>|ended|off`, `drops` — сколько обрывов входа было).
Это важно и для свежей вкладки: браузер без истории опросов не может отличить
«ключ умер 3 секунды назад» от «такого ключа никогда не было» и был бы вынужден
врать. Если supervisor старый (нет `/status`), панель пользуется своими опросами
и при отсутствии доказательств недавней публикации честно показывает красный.

**Типичная жалоба** «стрим идёт, а пишет Свободен»: почти всегда реальный обрыв
на стороне телефона, а не панели. Проверить: `docker logs --since 30m tl-mediamtx`
и искать `conn <IP телефона> closed: EOF` / `is publishing to path 'tatami/N'`;
`docker logs tl-supervisor` покажет `live:N -> fallback` в те же секунды.

**Ключи площадок** (VK/YouTube) не в QR и не в приложении — только в
`outputs/outputs.local.conf` (gitignored), правятся из карточки экрана
(блок «Куда транслируем», POST `/ctl/outputs` → ctl.py переписывает файл атомарно →
relayer подхватит за ~3 с, без рестарта). Смена ключа не требует пересканирования QR.

## 7. Какую нагрузку система может нести

### CPU / RAM (12 vCPU / 60 ГБ) — запас большой

- Ингест и все ретрансляции — **`-c copy` без перекодирования**: CPU-дешёво.
  8 входов + N выходов — для CPU не проблема даже при 4 Мбит/с на поток.
- HLS: на сервере `hlsAlwaysRemux: no` — муксится **только на активного зрителя**
  (в отличие от локального MVP, где 16 потоков remux-ились постоянно).
- Итог: 8 татами × несколько площадок + десятки зрительских превью на :8888
  система спокойно держит. RAM-узких мест нет (в простое 0.4 ГБ).
- Реальная граница — не CPU, а **исходящий канал VPS и квота трафика** (ниже).

### Трафик (главная экономическая величина)

- 1 татами ≈ 4 Мбит/с на **каждую** площадку. 8 татами × 1 площадка ≈ 32 Мбит/с
  постоянно ≈ **~346 ГБ/сутки**. Каждая дополнительная площадка на ту же букву
  удваивает расход по этой букве.
- Стоп-карты значительно дешевле live (~0.8 Мбит/с): в простое (телефонов нет)
  8 broadcast + 1 relay ≈ ~1 Мбит/с исходящего.
- Диск записи (если включить): 8 × 4 Мбит/с ≈ **~14.4 ГБ/час**; сейчас выключено.

### Сценарии отказов (что выдерживается)

| Сценарий | Поведение |
|---|---|
| Упало 1 из 8 телефонов | broadcast этой буквы → стоп-карта за ~2 с, остальные 7 не тронуты |
| Упала площадка (YouTube/VK) | ffmpeg relayer'а падает и ретраится каждый тик; broadcast и другие буквы не падают |
| Упал supervisor | broadcast-фидеры умрут (нет watchdog'а поверх контейнера); `restart: unless-stopped` поднимет контейнер, фидеры восстановятся < ~3 с — но **без systemd-монитора «выжил ли контейнер» это ручная проверка** |
| Упал mediamtx | падает всё (приём + feed + превью); docker поднимет, телефоны переподключатся сами |
| Падение VM/сервера | ничего не восстановится до перезапуска (HA нет) — см. §8 |

## 8. Слабые места и узкие горлышки

По убыванию критичности:

1. **Диск 79% занят (12 ГБ свободно из 59).** Причём стек стриминга весит
   ~50 МБ — объём съеден **чужими старыми контейнерами** (`postgres`, `n8n`,
   `qdrant`, `ollama` — проект n8n-tournament-expert, выключены 5–6 мес назад):
   их docker-волюмы — **~33 ГБ** (больше всего — `n8n-tournament-expert_ollama_data`
   и `..._postgres_data`). Пока они лежат — включение записи (14.4 ГБ/час!)
   упрётся в потолок за ~50 минут. Лечится чисткой старых волюмов после бэкапа.
2. **Нет redundancy (одна VM, один диск, один uplink).** Падение CT101 = падение
   всего эфира; авто-восстановление только в рамках живого Docker.
3. **UFW выключен** + RTMP `:1935` опубликован на 0.0.0.0 + auth `user: any`:
   любой в LAN может опубликовать свой поток на `tatami/*` и читать API через
   Caddy (BasicAuth). В приватной сети риск средний, но перед выходом в
   «боевую» сеть: включить UFW, сузить 1935 по source IP.
4. **Приватный IP** — телефоны только из этой LAN. Турнир вне сети = нужен
   публичный IP или порт-форвардинг роутера на 1935 (и новый QR).
5. **Дыра ~1–2 с** при каждом live↔fallback переключении (замена ffmpeg-фидера,
   а не бесшовный switch). «Ни одного кадра» = Liquidsoap (вне MVP).
6. **Жизненный цикл YouTube-ключей**: `live2`-ключ жив, пока трансляция не
   закрыта на YouTube. Закрыли сессию → relayer flapiet каждые 3 с (см. §6).
7. **Логи и мониторинга нет**: stdout-логи контейнеров (без ротации), алертов
   нет; «упал ли broadcast» видно только зайдя в панель. `record: no` — архива
   турнира на сервере нет (есть только на локальной машине, если стрим был туда).
8. **Расхождение репо и боевого сервера**: три фикса v1.21.2 (поле `password`
   в mediamtx, `handle` vs `handle_path` для `/v3`, bcrypt в Caddyfile)
   применены **только на сервере**; шаблон `deploy/vps/*` в git устарел — новый
   деплой по репо упадёт (см. `DEPLOY_VPS_RESTTIMER...md` §4).
9. **TLS нет** (домена нет → HTTP + BasicAuth по нешифрованному каналу; пароль
   панели летит в открытом виде по LAN). Домен + Caddy TLS — следующий шаг.
10. **8 татами — твёрдый потолок**: расширение = правка 6 мест (RELAY.md §9).


**Что нужно, чтобы работать с сервером:** только SSH-ключ (выше) и нахождение
в той же LAN, что и `172.22.22.17`. Пароль панели — в чате/у оператора (не в git);
сброс: `docker run --rm caddy:2-alpine caddy hash-password --plaintext 'НОВЫЙ'`
→ вписать в Caddyfile строку `basic_auth` → `--force-recreate caddy`.

**Что НЕ НУЖНО** (частые заблуждения):

- Пароль root-сервера — не используется, только ключ.
- Ключи VK/YouTube на сервер — не нужны: они в `outputs.local.conf`,
  вставляются из панели; QR телефонов ключи площадок не содержат.
- Сборка образов на рабочей машине — не нужна: сервер билдит сам (`--build`).
